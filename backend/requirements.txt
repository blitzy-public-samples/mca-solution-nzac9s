# Backend dependency manifest for Python 3.9, the runtime ci.yml line 19
# and Dockerfile.backend line 2 declare, so every pin resolves inside that
# envelope. Versions are exact because no lock file constrains them, and
# the pins carry two kinds of bound a range would let a resolver violate:
# hard compatibility constraints, and floors that keep known-vulnerable
# releases out of the image. What is declared is what this codebase requires
# across runtime, deployment and test concerns, plus the one provider bound
# that an extra leaves open; every other distribution is a resolver result.
# Advisories that survive because no remedy exists inside the Python 3.9
# envelope are recorded at the end of this file rather than left implicit.

# Web framework
# pydantic MUST stay below 2.0: app/core/config.py line 1 imports
# BaseSettings from pydantic, which 2.0 moved out to the separate
# pydantic-settings package. This pin is what keeps config.py working
# unedited, and it caps fastapi in turn - 0.126.0 is the first release
# that requires pydantic>=2.7.0, so 0.125.0 is the measured ceiling:
# anything above it resolves to ResolutionImpossible against the pin
# below. Held AT that ceiling, fastapi clears the CVE-2024-24762
# Content-Type ReDoS and, because 0.125.0 widens its own bound to
# starlette<0.51.0, resolves starlette to 0.49.3. That is what closes
# CVE-2025-62727, the quadratic-time Range header merge in FileResponse,
# on top of CVE-2024-47874 and CVE-2025-54121, two unauthenticated
# multipart denial-of-service vectors on the upload route below.
# starlette itself stays unpinned: it is a resolver result of this bound
# rather than a declared dependency.

# Security
# The cryptography extra is load-bearing, not decorative: it is what
# makes jose select its cryptography RSA and EC backends and leave the
# bundled ecdsa one idle. The floor is 3.4.0, which is where the
# CVE-2024-33663 algorithm confusion, the CVE-2024-33664 JWE decompression
# bomb and CVE-2024-29370 were all closed; 3.5.0 is the newest release
# inside the Python 3.9 envelope and carries no advisory of its own.
python-jose[cryptography]==3.5.0   # JWT at security.py line 2
# The bcrypt extra names the backend CryptContext selects at security.py
# line 8, but bounds it only at bcrypt>=3.1.0, so a clean resolve takes
# bcrypt 5.0.0. passlib 1.7.4 finalises that backend by hashing an
# over-length probe secret, and bcrypt 5 refuses anything past 72 bytes
# instead of truncating it: pip install and pip check both succeed while
# the FIRST hash or verify raises ValueError. The pin below therefore
# narrows passlib's own extra rather than adding a distribution, exactly
# as the pydantic and SQLAlchemy bounds above narrow theirs. 4.0.1 is
# measured, not preferred: bcrypt 4.1.0 dropped bcrypt.__about__, which
# passlib reads at handlers/bcrypt.py line 620, so 4.1.0 through 4.3.0
# hash and verify correctly but write 394 bytes of trapped AttributeError
# traceback on first use where 4.0.1 writes none. No advisory separates
# any of them, so a newer provider would buy noise and no security.
passlib[bcrypt]==1.7.4             # CryptContext at security.py line 8
bcrypt==4.0.1                      # provider of the passlib extra above
